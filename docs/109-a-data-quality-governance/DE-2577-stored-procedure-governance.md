# Governance & Release Procedure for Stored-Procedure Reporting Changes

Source document: [Linear document](https://linear.app/bitgo/document/governance-and-release-procedure-for-stored-procedure-reporting-fdcd772ac8a1)

Related issue: [DE-2577](https://linear.app/bitgo/issue/DE-2577/design-governance-mechanism-for-stored-procedure-report-changes)

## Purpose

Client-facing CSV/PDF reports are generated by Snowflake stored procedures. Existing API schema checks cannot detect changes inside those procedures because the API returns opaque report files. This creates a risk that column order, types, filtering, or calculations change without a client-impact review.

## Decisions

- New columns must be appended to the end of an existing report.
- Inserting a column in the middle is blocked unless the report receives a new major version.
- Removing or renaming columns is a breaking change.
- Reordering columns is a breaking change because downstream clients may parse files positionally.
- Semantic filtering changes that alter row inclusion are breaking changes.
- Data-quality fixes that change historical totals require release notes and client communication.

## Change tiers

### Tier 1 — Breaking change

Examples: removing or renaming a column, reordering columns, narrowing a data type, or changing row-inclusion semantics.

Required controls: a versioned stored procedure such as `_v2`, 30–60 days of notice, Product/CSM/DevX/technical approvals, a deprecation schedule, and client communication.

### Tier 2 — Additive change

Examples: appending a column or widening a data type.

Required controls: 14 days of notice, release notes, and Data Engineering/Product review.

### Tier 3 — Data fix or performance change

Examples: calculation correction, duplicate removal, or query optimization.

Required controls: normal review and deployment, release notes, and client notification when historical totals or balances change.

## Proposed technical controls

- Maintain an ordered `proc_manifest.yml` contract with column position, name, and type.
- Compare changed procedure schemas against the baseline in CI.
- Fail CI on dropped, renamed, reordered, or incompatible columns.
- Allow compatible new columns only at the end of the report.
- Use parallel `_v1`/`_v2` procedures for breaking changes.
- Require a release checklist covering procedure name, change tier, schema position, manifest update, tests, client impact, release notes, and approvals.
